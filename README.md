## 2. 它能做什么 / 不能做什么

**能做的：**

- 登录校园跑 App 的服务器，查询自己当前已跑总里程；
- 伪造一条看起来合理的跑步轨迹（坐标点 + 配速 + 耗时）上传，让服务器认为你跑完了；
- **写死学号后全自动运行**：启动 → 登录 → 上传 → 回查，全程不需要手输；
- **穿越时间**：把跑步记录伪造成过去某一天，一天一条，从而在一天之内把几个月的量补完（用于突破单日 4km 限制）。

**不能做的（重要）：**

- 不能改学校代码以外的东西——**学校代码是写死在代码里的**，换学校要自己改源码；
- 不会绕过任何"需要真机传感器"的校验——它做的是**直接和服务器对话**，不是模拟手机；
- 不保证长期可用：**服务端随时可能加签名、校验轨迹、封号**，这个脚本没有对抗能力；
- 不能"安全"——学校如果抽查轨迹轨迹、配速、设备号、时间分布，是有可能被发现的。

## 3. 它是怎么工作的（原理）

整个方案的核心是：**抓包拿到 App 和服务器之间的三个接口，然后用 Python 直接模拟 App 发请求。**

App 用的是 HTTP（不是 HTTPS），请求体基本都是 `gzip` 压缩后的 JSON，服务器地址形如
`http://222.28.94.116:8030/DragonFlyServ`。

### 3.1 登录：密码就是 md5(学号)

`main.py` 里的 `login()` 发两个请求：

1. `bangding`——绑定预处理，返回值不参与判断；
2. `bangdingschool_local`——本地绑定登录，参数里带学校代码、学号、密码、机型（`HarmonyOS`）、`android`、版本号。

**关键点：这个 App 的默认密码就是学号的 md5。** 所以只要有学号，就能算出密码登录，不需要知道任何人的真实密码：

```python
password = hashlib.md5(stuno.encode()).hexdigest()
```

登录成功的响应是 `xxx,<uid>` 这种格式，脚本取逗号后面的部分作为 `uid`，后续所有请求都要带它。

### 3.2 查里程

`getinfo()` 请求 `/Api/webserver/getRunDataSummary`，拿到一段文本，里面有一句：

```
校内定向跑:15.915公里
```

脚本用正则 `校内定向跑:([\d\.]+)公里` 把数字抠出来。这就是"当前已跑多少公里"的来源。

### 3.3 上传：自己造一条轨迹

`upload_run()` 请求 `/Api/webserver/uploadRunData`，请求体里有这几个关键字段：

| 字段 | 含义 | 脚本怎么填 |
| --- | --- | --- |
| `begintime` / `endtime` | 开始 / 结束时间戳 | 由"你声称跑步的时刻"倒推 |
| `distance` | 距离（米） | 你配置的目标距离 |
| `speed` | 平均速度 | `distance / usetime` |
| `usetime` | 总耗时（秒） | `距离 / 1000 × 配速`，配速在 210~450 秒/公里间随机 |
| `location` | 轨迹点串 | **自己生成的假轨迹**，见下 |
| `path` | 抽稀后的轨迹 | 从 `location` 里抽 4 个点 |
| `atttype` / `eventno` / `ruleid` | 活动类型、赛事号、规则号 | 写死 `3` / `802` / `3` |

**`location` 的格式**（这是整个伪造里最核心的部分）：

```
纬度,经度;null;null;null;null;null@纬度,经度;null;null;null;null;null@...@888,888;结束时间戳;null;null;null;null
```

- 普通点：`纬度,经度` 后面补 5 个 `null`；
- 点与点之间用 `@` 连接，间隔固定 4 秒（服务端按这个还原"你每 4 秒在哪儿"）；
- **结尾是一个哨兵点 `888,888`**，后面跟结束时间戳——服务端靠它判断"这条轨迹结束了"；
- 脚本用"直线 + 每点微小随机抖动 + 每 10 个点拐一次弯"的方式生成坐标，这样轨迹看起来不像一条完美的数学直线。

**为什么能骗过服务器？** 因为据观察，这几个接口**没有做请求签名校验，也没有校验轨迹和真实 GPS / 设备指纹的绑定关系**——服务器基本上信任客户端上报的一切。它能成功，靠的就是这一点。一旦校方在服务端加上签名或轨迹合理性校验，这个脚本就会立刻失效。

### 3.4 轨迹和公里数是自动生成的

跑前什么都不用准备，脚本自己把「公里数 + 配速 + 轨迹」整套生成出来：

- **公里数**：`RUN_DISTANCE_M = 0` 时，每次运行在 `DISTANCE_RANGE = (3900, 4100)` 里随机取一个值，而不是永远固定的 4000m——**历史记录里每天的距离都不一样**。
- **配速 / 耗时**：在 `PACE_RANGE = (330, 480)` 秒/公里之间随机，换算成 `usetime` 和 `speed`，大约 7.5~10.9 km/h，是学生慢跑的合理区间（原版写的是 210~450，折合最高 17 km/h，明显像骑车，我收窄了）。
- **轨迹**：`generate_mock_path()` 从 `START_LAT / START_LNG` 出发，每 4 秒生成一个点，方向每 10 个点轻微拐弯，避免轨迹是数学意义上的一条直线；`LOOP_BACK = True` 时**跑到一半掉头做折返跑**，终点会回到起点附近。
- **自洽性**：生成的轨迹总长度与上报的 `distance` 基本一致（实测上报 4000m → 轨迹实测 3998m，终点距起点约 120m，最远点约 1990m），如果服务端校验「轨迹长度 ≈ 上报距离」也过得去。
- 运行时会直接打印结果，方便你确认它到底造了什么东西：

  ```
  [*] 轨迹已自动生成: 300 个点 / 耗时 1200s / 配速 300s每公里
  ```

## 5. 配置说明（学号 / 里程 / 学校代码）

所有可调的东西都在 `main.py` 顶部的 **「① 配置区」**：

```python
# 学校代码：写死在代码里。10032 = 北京语言大学
SCHOOL_NO = "10032"

# 学号：填上就全自动，启动后不再需要手输；留空则启动时提示输入
STUDENT_NO = ""            # 例如 "202400000000"

# 单次跑步距离（米）
#   填数字（如 4000）：每次都跑这个固定距离
#   填 0            ：每次在 DISTANCE_RANGE 里随机（推荐）
#   填 None         ：启动时手动输入
RUN_DISTANCE_M = 0
DISTANCE_RANGE = (3900, 4100)

# 启动模式：0 = 询问；1 = 只跑一次；2 = 穿越时间补到目标总里程
AUTO_MODE = 0
TARGET_TOTAL_KM = 100.0
TIME_TRAVEL_START_DAYS = 365
```

**实际上你日常只需要改两个东西：学号、跑步公里数。**

- **学校代码**：写死在 `SCHOOL_NO` 里，默认 `10032`。换学校要自己改这个值，**顺便大概率还要改 `BASE_URL`**（服务器地址），因为每个学校用的是自己的服务器。想知道自己的学校代码，可以用抓包工具（Charles / Fiddler / HttpCanary / mitmproxy 之类）登录一次 App，看登录请求里的 `school` 参数。
- **学号**：填进 `STUDENT_NO`，就不用每次手输了。
- **公里数**：`RUN_DISTANCE_M = 4000` 就是每次都跑 4 公里；改成 `0` 就变成**每次在 `DISTANCE_RANGE` 里随机**（推荐，见 [§3.4](#34-轨迹和公里数是自动生成的)）。
- **全自动**：`STUDENT_NO` + `RUN_DISTANCE_M` + `AUTO_MODE = 1` 都填好，之后 `python main.py` 直接跑完退出，可以挂到计划任务/开机自启里，真正做到"写死学号后自动启动、自动跑"。

一个最小的全自动配置长这样：

```python
SCHOOL_NO      = "10032"
STUDENT_NO     = "你的学号"
RUN_DISTANCE_M = 0        # 0 = 每次自动随机 3.9~4.1km
AUTO_MODE      = 1
```

## 6. 穿越时间：一天跑超过 4km

正常情况下，这个系统一天只认一次跑步记录（单次大约 4km 封顶，所以 `DISTANCE_RANGE` 默认取 3900~4100 米，就是照着这个经验值来的）。

但它有一个漏洞：**服务端直接信任客户端上报的 `begintime` / `endtime`。** 也就是说，你这次上传说自己"上周三下午 5 点跑的"，服务器就真的记到上周三。

所以 `AUTO_MODE = 2` 的「暴走模式」是这么刷的：

1. 先从 **一年前** 开始（`TIME_TRAVEL_START_DAYS = 365`）；
2. 每次挑一个下午到晚上的随机时刻，用 `DISTANCE_RANGE` 自动生成一条 3.9~4.1km 的记录上传；
3. 上传后立刻回查总里程，涨了就算成功；
4. 日期往后推一天，继续下一条；
5. 一直补到 `TARGET_TOTAL_KM` 达标，或者补到"今天"就强制停手（避免覆盖真实数据）。

**结果就是：人只坐了一会儿，账号里多出了几个月的跑步记录。**

脚本也做了几个自保设计：每轮之间 `sleep(3)` 等落库、连续 5 次不成功就自动中止、补到今天就停。但**这些只是降低"把账号刷成异常"的概率，不是安全保证。**

## 9. 常见问题

**Q：登录失败怎么办？**
A：先确认学号、`SCHOOL_NO`、`BASE_URL` 是否匹配；再确认网络能访问到学校服务器（有些校园网/内网才能访问）；最后确认 App 的登录方式有没有改版。

**Q：上传"成功"了但总里程没涨？**
A：最常见的原因是**那天已经有记录了**（一天只能记一次），或者单次距离超了上限。穿越模式遇到这种情况会自动翻到下一天。

**Q：会不会被封号 / 被处分？**
A：**有可能。** 服务端如果做轨迹合理性、设备指纹、时间分布、异常频率的校验，这个脚本没有任何对抗手段。学校也完全可能人工抽查。风险请自行评估。

**Q：需要我提前准备轨迹文件吗？**
A：不需要。公里数、配速、坐标点全是运行时自动生成的，`main.py` 里没有任何需要你提供的轨迹数据。

**Q：为什么只支持一个学号？**
A：这个开源版只保留了单账号的 `main.py`。批量多账号的版本（用来给别人代跑的）**没有放进来**，一是那部分要读一份含真实学号的表格，二是我也不希望它被拿去干代跑这种事。
